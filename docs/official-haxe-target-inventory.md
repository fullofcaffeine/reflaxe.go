# Extended official Haxe target inventory

This is the broad, slower companion to the fast
[official Haxe target smoke](official-haxe-target-smoke.md). It answers a
specific question: “Of the tests shipped in Haxe 4.3.7's portable `tests/unit`
families, which ones can Haxe.Go run today, which ones genuinely do not apply,
and which ones expose work we still need to do?”

The current pinned inventory contains 1,211 source owners. A source owner is an
upstream test class or specification, not a raw file count used as a quality
score. The verified local baseline is:

| Status | Owners | Meaning |
| --- | ---: | --- |
| Active | 607 | At least one positive upstream test method ran on generated Go. |
| Blocked | 472 | The behavior applies, but a named compiler, generated-Go, runtime, or typed-harness gap prevents a trustworthy pass. |
| Inapplicable | 132 | The pinned upstream Go selection has no active fixture, the file is support code, it belongs to another target, or it needs a separately named environment. |

Those 607 active owners contain 650 runtime test methods and 1,910 upstream
assertions. “Blocked” is intentionally not rewritten as “inapplicable” to make
the score look better.

## What “tested as a real Haxe target” means

Every active shard follows the same real user path:

1. Build a fresh Haxelib ZIP from the current Haxe.Go checkout.
2. Install that ZIP into an isolated Haxelib repository.
3. Ask Haxe 4.3.7 to compile unchanged official behavior bodies with the
   installed `reflaxe.go` backend and the portable preset.
4. Run `gofmt` over every generated Go file.
5. Run strict `go test ./...` and `go build ./...` checks.
6. Execute the generated Go program and collect the upstream test identities
   and assertion totals it actually completed.

This is stronger than checking generated text. It proves that the packaged
custom compiler, Haxe macro integration, generated Go project, Go toolchain,
and target runtime work together for the recorded tests.

## What the result does—and does not—claim

This evidence belongs only to the portable compiler scorecard
(`portable-compiler`) in
[`test/testing-strategy.json`](../test/testing-strategy.json). It does not
admit an API in the public compatibility manifest by itself. In other words,
the inventory does not admit new public support; it also does not
prove:

- the `metal` convenience preset or explicit Go-native APIs;
- all Haxe language behavior, including the 472 blocked owners;
- public networking, runtime operations, or platforms not separately admitted;
- Windows or macOS runtime behavior from a Linux result;
- downstream packages, examples, diagnostics, or source maps.

The fast three-family smoke stays on every required pull request because it is
the economical tracer bullet. The complete inventory runs cold on Linux for
both supported Go versions in R4 (master and weekly) and blocks R5 release
publication. A green extended lane cannot substitute for the required smoke,
and a green smoke cannot be reported as complete inventory coverage.

## Why typed adapters exist

The upstream suite has its own test runner and support inheritance. Running the
entire upstream runner would accidentally make unsupported test-framework
reflection part of every compiler claim. The inventory therefore creates a
small typed adapter for each shard:

- the official test method bodies and assertions stay unchanged;
- only helper bodies referenced by that shard are copied from pinned
  `unit.Test`, with visibility opened so the isolated subclass can call them;
- each direct test owner inherits a nominal typed harness interface;
- `unitstd` statements are read by the pinned upstream `UnitBuilder` and placed
  in a typed wrapper;
- every original and adapted source digest is written to the evidence artifact.

This is scaffolding, not an alternate expected-value generator. If the pinned
upstream structure changes, the adapter fails rather than guessing. Remaining
adapter limitations stay blocked under `haxe_go-vfp.12.12.4`.

## Commands

Run the complete claim-bearing check:

```bash
npm run test:official-haxe-inventory
```

Three local baseline runs on 2026-08-02 used Haxe 4.3.7 and Go 1.25.6 on
Darwin/arm64 and took 141.356, 156.516, and 152.086 seconds. Every run rebuilt and
installed the package into a clean temporary home; only machine tool caches
could be warm. The second sample being slower is a useful warning not to read
these measurements as a stable benchmark. CI supplies the release-relevant cold
Linux evidence on Go 1.25.12 and 1.26.5.

For troubleshooting only:

```bash
python3 test/run-official-haxe-target-inventory.py \
  --owner-regex '^unit/issues/Issue10752\.hx$' \
  --propose-baseline
```

`--owner-regex`, `--only-shard`, and `--propose-baseline` mark their result as
non-claim evidence. `--discover-blockers` recursively isolates a failed shard
and writes a rejected blocker proposal; it is a maintainer bootstrap tool, not
ordinary CI and not a way to bless failures. Baseline changes require semantic
review of the upstream behavior and the reason for every classification change.

The normal artifact is
`.cache/official-haxe-target-inventory/artifacts/result.json`. It records the
exact source commit and dirty-state digest, toolchains, installed package hash,
upstream pins, classifications, adapters, shards, runtime assertions, and
elapsed time without machine-local paths.

## Follow-up ownership

The durable blocker burn-down is `haxe_go-vfp.12.12`, split so each fix can use
the smallest faithful test:

- `haxe_go-vfp.12.12.1`: Haxe target-compilation failures;
- `haxe_go-vfp.12.12.2`: invalid or unbuildable generated Go;
- `haxe_go-vfp.12.12.3`: generated-target runtime semantic mismatches;
- `haxe_go-vfp.12.12.4`: unsupported typed upstream harness forms.

The exact blocked owner records remain in the versioned inventory files. Those
Beads group shared causes; they do not hide or replace the individual evidence.
